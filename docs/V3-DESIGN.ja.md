# v3設計: モデルへ渡る直前の観測量をHooksで管理する

更新日: 2026-09-24。実装対象は公開Hooks仕様。Codex CLIとの結合は未検証。

## 狙いと非目標

v2が毎回適切に`capture.py`を使い、検索出力も常に狭くしていたなら、追加効果は小さい。
v3の主目的は、その運用が漏れたときに毎回モデルへ注意して再試行させる代わりに、決定論的に出力を保存・縮小することである。
コマンドの実行コスト、Reader自身の入力、推論出力を直接減らすものではない。

非目標は、汎用shell解析、ソースコードの意味要約、LLMによるHooks、モデルルーティング、テストの合否判定、
全API呼出しへの課金上限、sandboxの代替、Codex会話履歴の書換えである。

## 主経路

```text
親または子のBashツール
  │ 元のコマンドは変更せず一度実行
  ▼
PostToolUse
  ├─ 未対応/小さい/原文読取り/複雑なshell → 無言で通す
  ├─ audit → 分類とバイト数を記録し、無言で通す
  └─ enforce + 対応する大きなテスト/検索応答
        │
        ├─ tool_responseのJSON値を正規化してprivate blobへ保存
        ├─ SHA-256・元の終了情報・受付メタデータを記録
        ├─ 保存失敗 → 元応答を保持。置換しない
        └─ 保存成功 → continue:false + stopReason内の短い返却
                           │
                           ▼
                  親は必要時のみ原文の行/byte範囲を再取得
```

`stopReason`の内容はPostToolUseのツール結果へのフィードバックである。
`additionalContext`に生のログを入れ、開発者指示として扱わせる設計にはしない。
`decision:block`やexit 2はcode mode内でpromiseをrejectするため、通常のログ削減では使用しない。
`updatedMCPToolOutput`/`suppressOutput`は現行公開仕様で未サポートなので使用しない。

## なぜPreToolUseでコマンドを自動書換えしないか

現行仕様では`permissionDecision:allow`と`updatedInput`で書換え可能だが、本版では使わない。
検索や`cat`を勝手に別コマンドへ変えると、元の期待する出力・終了状態・作業ディレクトリ・承認との対応が曖昧になる。
さらに未知のshellを解析してwrapするより、実行済みの限定した結果へ作用する方が副作用を増やしにくい。

残る欠点は、元のツール実行量を減らせないこと、上流で切り捨てられたログを復元できないこと、
code modeのJSが元結果を再出力すれば再流入することである。こうした経路にはv2の明示的captureを使う。

## 原文と参照の区別

探索報告やログの保存物は、その時点の観測である。ハッシュが一致しても、現在のソースに対する意味的正しさを示さない。
編集時は既存の`evidence.py`で現在の関数・型・テスト等を読む。原文取得の`cat/sed/head/tail`は自動置換しない。
返却を短くしたことを「この範囲だけで考えよ」という制約にしない。

検索は固定文字列を使い、保存ログに含まれる行番号だけを返す。該当行の取得は別のbounded readで行う。
巨大な一行の一致をそのままモデルへ返すことを防ぐ。スコープ内に見つからないことは、リポジトリ全体での不存在を意味しない。

## 終了状態の保持

既知のJSON形状に含まれる整数の`exit_code/returncode/exit_status/code`を明示的に保持する。
返却に終了状態がなければunknownとし、出力文字列に"passed"が含まれる等の理由で成功判定しない。
タイムアウト・省略情報が既知の形で付いていれば保持する。未知の構造化レスポンスやlive sessionは置換しない。

原文プレビューはUTF-8の先頭と末尾。省略した中央に原因がある可能性を必ず示す。
省略部分を推測で補うこと、単にツール返却を短くしただけでテストが通ったと扱うことは禁止する。

## 保存の不変条件

1. 置換するより先にblobを書き、fsyncして、台帳へ記録する。
2. artifact_idは正規化したtool_response JSONのSHA-256。復元時に再検証する。
3. blobは同一内容なら再利用するが、モデルへ渡す観測自体を勝手に省略するdedupではない。
4. 容量超過・書込み失敗・台帳失敗時は、元応答を置換しない。
5. 一時ファイルを含むblob領域に容量制限を設ける。DB領域は別なので利用者が容量を監視する。
6. 自動GCは行わない。利用者が復元不要を確認してから保存領域を削除する。

保存物は元のJSON値を失わないが、入力JSONの空白・キー順までは保持しない。
上流で既に出力が省略されていれば、その省略済み値しか保存できない。stdout/stderrの完全保存とは区別する。

## native起動上限

`PreToolUse`のspawn_agentを任意で監視する。
キーはSHA化したsession_id, turn_id, tool_use_id。SQLiteのBEGIN IMMEDIATEで受付判定を直列化する。
同じtool_use_idと同じ入力の再通知は同じ判断を返す。入力を変えて同じidを再使用したら拒否する。
roleフィールドの有無に依存せず、認識したnative spawnをすべて数える。

他Hookによる拒否・起動失敗でも受付枠を返さない。起動できた数ではなく、受付けた試行数の保守的な上限である。
既存セッションへ続きの仕事を送る操作、別turn、外部プロセス、Hookの対象外経路は含まれない。
親子のHookは同じsession_idを共有し得るが、turn_idまで同じとは仮定しない。
従って、タスク全体/子孫全体の制限とは称さない。

初期値0で無効。一般的なマルチエージェント作業を妨げないよう、Explorer/Solver運用で明示的に2等を選択する。
上限を有効化したのに会計できない場合はspawnを拒否するが、Hook自身の未発火・未認識まで防げる安全境界ではない。
監査モードでは越境を記録しても拒否しないので、台帳の数を実際の開始/停止数と混同しない。

## Compaction

PreCompactで直近3件までの保存物参照だけをsnapshot化する。本文や会話を読むこと、追加要約を呼ぶことはしない。
SessionStart(source=compact)ではそのsnapshotを、resumeでは現在の直近参照を使い、最大1,024 byteの復元案内を返す。
後から到着した別ツールの保存物をcompact前のsnapshotに混ぜない。

元ログは残っているため、compaction後もログ取得だけを理由にテスト/探索を最初から実行し直す必要はない。
ただしプログラムが変更された後の再テストは別であり、古いログを新しい成功証拠として使ってはいけない。

## Hookの組合せ

自分の判断は一つの同期ディスパッチャー内で完了させる。複数の自分用Hooksを順序依存で繋がない。
外部のHookや既存のv2 read_guardは残す。別のHookは同時に動き、拒否や追加コンテキストを返すことがある。
本キットの保存成功で、他Hookの動作・副作用を打ち消せるとは仮定しない。

`configure_hooks.py`は既存のJSONを読み、所有manifestと完全一致するグループだけを更新する。
未知/独自編集のグループは削除しない。適用前backupと楽観的並行更新チェックを行う。
複数ファイルの置換は完全なOSトランザクションではない。異常時の復旧用に変更前ファイルを必ず残す。
信頼・sandbox・managed policyを迂回せず、適用後は`/hooks`で利用者が確認する。

## 測定

単なる文字列の圧縮率を総トークン/費用の削減率と呼ばない。
ローカル指標は、分類別の観測件数、Hookに届いた応答JSONバイト数、Hook返却JSONバイト数、保存失敗数、
native受付判断数である。`token_savings`と`billing_savings`は未計測としてnullにする。

実環境では少なくとも、親/子の全使用量、キャッシュの内訳、復元した量、成功率、Hookによる遅延を測る。
条件A=v2、条件B=v3 audit、条件C=v3 enforceを同じ課題・モデル・推論設定・テスト条件で比較する。
Bは性能の基準ではなく、追加遅延と対象量を測るための比較である。

一回のログが小さい作業や、v2の明示的captureが既に徹底されている作業では、本Hookが遅いだけになる可能性もある。
その場合は登録を無効化する。常に有効化することを目的にしない。

## 検証の範囲

- 単体/回帰: 境界サイズ、Unicode、exit status、保存失敗、復元、並行受付、Hook設定の更新/削除。
- smoke: 実際のローカルunittestで意図的な失敗ログを生成し、人工Hook envelopeへ載せ、保存/復元をCLI越しに試す。
- v2 ZIPを指定したsmoke: そのpayloadからの更新と、ユーザーの設定/無関係Hookの保持を試す。
- 未実施: 実CodexのHook発火、code modeにおける全経路、修正成功率、実際のトークン/費用比較。

ログのバイト削減値はローカルfixtureの結果だけである。公開論文やSpotify記事の効果量を本版へ割り当てない。
