# v2 設計仕様・評価計画

確認日: 2026-09-24。これは実装の設計判断であり、論文の追試結果ではありません。
引用先は `SOURCES.md` の番号に対応します。

## 1. Spotifyの記事から採用した境界

Spotifyの事例[1,2]から採用したのは、I/O中心の処理を主モデルから外すこと、ルーティング規則をスクリプトとフックで補助すること、
編集用の原文取得経路を残すことです。「90%」を全worker込みの費用削減や一般的な修正品質の保証としては扱いません。
Portalのモード管理・APIを本キットの依存先にはせず、Codexの公開インターフェースへ置き換えます。

そのまま採用しなかったのは、親が生成結果を確認せず本番作業ツリーへ保存するcode-writerです。
本キットでは親が仕様・修正・検証を持ちます。生成専用workerの追加は、差分の検査、独立したテスト根拠、適用先の隔離が必要になります。
これらを省いて出力トークンだけを減らす構成にはしません。

## 2. 実行グラフ

```
課題
  ├─場所が既知の編集/推論 ───────────────────→ 親が必要な原文を読む
  ├─既知ファイル・文字列の照合 → deterministic search ─┐
  ├─既知ファイル・意味を伴う事実質問 → cheap Reader ────┤
  └─場所が未知 → cheap Explorer ───────────────────────┤
                                                       ↓
                                              根拠参照の検証
                                                       ↓
                                               親が必要な原文
                                                       ↓
                                                編集 → テスト
                                                       ↓
                                   raw logsは外部保存、短い原文を表示
```

ExplorerとReaderは並列で常用する二段階ではありません。異なる入力条件への代替経路です。
Readerが存在するからといって、既知の小さな関数までReaderに送り直しません。
RLM研究[3]は長い入力を外部環境として扱う発想を支持しますが、v2は再帰型モデルの実装・学習・再現実験ではありません。
本キットで採用するのは、モデルに入れなくても実行できる抽出を先に行う、という境界だけです。

## 3. 再利用するものと再計算するもの

既に親が保持している原文を、変化がないのに再取得するのを避けます。
ハッシュは実ファイルの未commit変更も検出します。Git HEADだけでは代用しません。
行番号は索引であり、不変の識別子ではありません。ハッシュが変わればシンボルを再検索します。

意味的な回答キャッシュは実装しません。引用されたファイルだけのハッシュで探索結果をキャッシュすると、
未引用ファイルの変更や新規ファイル追加により、過去の「見つからない」が誤って再利用されるためです。
質問・全探索対象・モデル/指示/設定・追加/削除を含む依存集合の確実な無効化を実装せず、キャッシュが安全だとは主張しません。
固定コーパスReaderは未引用も含む全入力の現在ハッシュを検証しますが、異なる質問間の回答共有は行いません。

またCodexの会話prefixを途中で書き換える圧縮や自動compactionの再設定は行いません。
キャッシュ利用と再読込みで経済効果が変わるという観点[4]を、実装の節度と計測項目へ反映しています。

## 4. 返却契約

既存のhandoff version 1を維持します。

- primary: 最大3件、related: 最大2件。path/start/end/sha256/symbol/evidence。
- readyは限定された有用な参照があること。根本原因の正解や修正影響範囲の網羅性を意味しない。
- partialは有用な入口があり未解決事項も残ること。捨てたり自動昇格したりしない。
- not_foundは調べた範囲に対する不一致。リポジトリ全体の不存在ではない。
- blockedは具体的な環境・役割上の制約。無限のモデル切替えで解決しない。

自然言語は、原文を探すための短い事実説明だけに使います。編集対象コードの代用品にはしません[6]。
機械検証できるのは構造、容量、パス、範囲、ハッシュ、Readerの指定コーパス所属です。
「evidenceの文章がその行から本当に導けるか」は親の確認対象として残ります。

## 5. 数値予算の意味

| 制御 | 初期値 | 実装上の意味 |
|---|---:|---|
| 直接読取りの目安 | 12,000 UTF-8バイト | heuristic。トークン換算しない |
| 検索入力 | 明示12ファイル・合計2 MiB | 決定的検索の範囲制限 |
| Reader入力 | 明示12ファイル・原文64 KiB | スクリプトが送る原文の制限。番号等のオーバーヘッドは別 |
| Readerスナップショットのシリアライズ | 最大128 KiB | エスケープ・行番号による膨張も制限 |
| 検索の表示 | 通常20件・最大50件 | byte上限も適用。続きありを明示 |
| handoff | 6,144バイト・最大5参照 | 出力を原文の索引に制限 |
| 原文範囲 | 1回160行、索引合計480行 | 必要な追加読取りは禁止しない |
| 外部worker | 1タスク2起動、同時1 | 同じSTATEを使うlocate.pyだけに強制 |
| Deep Explorer | 上の枠内で最大1起動 | 事前の低コスト試行が必須 |
| 子のshell回数 | Explorer10、Deep16、Reader6 | モデルへの指示。物理的上限ではない |
| ローカル期限 | Explorer/Reader初期120秒 | ローカルプロセスの停止期限。課金キャンセル保証ではない |
| 保存ログ | 16 MiBを監視 | ポーリングによる停止。厳密なバイト境界ではない |

これらはすべて設計上の初期値で、論文の最適値ではありません。
Readerの外部snapshotモードは原則tool不要ですが、無toolは指示であってCLI機能による全面禁止ではありません。
子起動1回は、内部のモデルAPI要求が1回であることを意味しません。

## 6. 起動予算の状態機械

```
未登録 → reserve（SQLiteトランザクション） → running
                                      ↓
                         完了/不正応答/失敗/期限/割込み
                                      ↓
                                   finished
```

runningがあれば別起動を拒否します。失敗を含む全予約を起動回数に算入します。
終了使用量が未知なら次の起動を初期設定で拒否し、未知を0に変換しません。
強制終了で残ったrunningは自動期限切れにしません。実プロセスを確認し、手動のmark-abandonedで未知消費として確定します。

soft-token-limitは観測済み量による**次回の起動判定**です。
まだ終わっていない要求のトークン数も、別のSTATE・native子・親・別CLIの消費も拘束しません。
呼出し回数制限をAPI課金のハード上限として宣伝しません。
条件付き昇格の考え方はIssueLoc論文[5]を参考にしていますが、我々の閾値やend-to-end修正効果は未検証です。

## 7. フックを安全境界にしない

Codexの公開PreToolUse契約[9]を使い、対応した単純な読取りを実行前に検知します。
監査モードから始め、実際の呼出し形と誤検知を確認した後だけdenyへ変えます。

正規表現を増やして任意のshellプログラムを「安全/危険」と完全に判定できるとは考えません。
パイプ、変数展開、複合文、独自Python、MCP、特殊toolはこのガードの外です。
不明な入力やinspect失敗は通しますが、安全と証明したことにはしません。
Nativeの親子は共通session_idになり得るため、session_idだけで子を除外しません。

過剰出力をPostToolUseで無差別に削る機能も実装しません。
削る対象を誤って失敗証拠・終了状態まで消さないよう、まず明示capture経路を使います。
旧観測を除く研究[7]やgoal-guided pruning研究[8]は参考ですが、v2がそのハーネス操作・学習済みskimmerを再現したわけではありません。

## 8. テスト出力の保全

captureはstdout/stderrを分けて保存し、元プロセスの終了コードとwrapperの終了理由を別々に返します。
親に返すのは意味要約でなく短い原文末尾です。全文が必要ならログへの参照を辿れます。
プロセス終了0はそのコマンドの終了状態でしかなく、受け入れ条件すべての合格を意味しません。
テストの実行自体はモデルを呼ばなくても、プロジェクトコードの副作用を起こし得ます。通常の実行権限・sandboxを利用者が管理します。
対話式プログラム・任意のdaemon管理は対象外です。captureは親プロセスを観測するラッパーです。

## 9. 費用・tokenの評価

目的を3つに分けます。

1. 親が処理するtokenを減らす。
2. 全worker+親のtokenを減らす。
3. 全worker+親の実費用を減らす。

これらは同値ではありません。低単価モデルへの移転は2を改善せず3だけを改善する可能性があります。
キャッシュも考慮した各modelの費用は概念上、未キャッシュ入力、キャッシュ入力、出力を別単価で積算します。
reasoningを出力へ、cached inputを総inputへ再加算してはいけません。

委譲の有効性は「直接実行の費用」と「worker費用 + 親の索引読取り + 原文再読取り + 増えたturnの費用」で比較します。
親へ返す文章の短さだけを成功基準にしません。

推奨するアブレーション:

| 条件 | 有効な追加要素 |
|---|---|
| A | 親のみ |
| B | v1のExplorer/Solver分離 |
| C | B + 決定的抽出 + capture |
| D | C + 必要時Reader |
| E | D + 監査後のread-guard deny |

同じ課題・モデル・受け入れ条件・初期作業状態で複数回比較します。
小さな一回差を結論にせず、まず失敗・再読取り・委譲率と差のばらつきを確認します。
キャッシュ条件の違いを記録し、実行順を混ぜます。

主指標:
`全試行（失敗込み）の全worker・親のinput+output token合計 / 外部判定の成功数`。

補助指標は親/子別input/output/cached input、起動数、実測遅延、再読込み量、JSON不成立率、
引用と主張の不整合率、誤ったnot_found、誤ブロック率です。
本キットは親の全課金を自動回収しません。計測不足の試行を黙って除外したり、workerだけから全体の削減率を出したりしないでください。

## 10. 採用を見送ったもの

全コードのLLM要約、常時並列agent、全文graphの常駐、埋込みDB・再ランキングサーバー、
自動的なモデル昇格ループ、未レビューのcode-writer、依存集合が不完全な回答キャッシュ、
任意shellを完全に制御できるという前提、auto-compactionの独自置換は追加していません。
どれも必ず悪いわけではありませんが、この段階で運用負担や追加消費を増やす根拠は足りません。
